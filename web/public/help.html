Getting Started

Install and bring up your first Minimal Router VM

There are two recommended paths. Use the ISO when you want the most repeatable appliance install. Use an AI-assisted workflow when an agent has access to your Proxmox/Git environment and you want help creating, checking and validating the VM.

Option A — ISO install

Best for a clean, reproducible deployment. Create a small Alpine-compatible VM, attach the Minimal Router ISO, give it two NICs, boot from ISO and follow the installer/setup flow.

Option B — AI-assisted VM setup

An AI coding/ops agent can guide or automate the repetitive steps when it actually has access to your Proxmox host or repository: create the VM, attach NICs/ISO, run installation commands, inspect logs and verify health.

VM layout

  • NIC 1 — LAN: connected to the bridge used by your home/office clients or management LAN.
  • NIC 2 — WAN: connected to the bridge/physical port that reaches the ISP/ONT. PPPoE runs on this side.
  • CPU/RAM: Minimal Router is designed to be lightweight. Start small and increase only if your workload requires it.
  • Disk: keep enough space for Alpine, A/B firmware slots, logs, snapshots and encrypted backups.
Important: verify which virtual NIC maps to WAN and which maps to LAN before enabling PPPoE. Reversing them can disconnect management or put the wrong network on the ISP-facing side.

ISO path — step by step

  1. Create the VM in Proxmox and attach two virtual NICs.
  2. Attach the Minimal Router ISO and boot from it.
  3. Install to the VM disk and reboot from disk.
  4. Open the Proxmox console and confirm the detected interfaces.
  5. Open the dashboard from the LAN side and complete the first-run setup wizard.
  6. Enter the PPPoE username/password from your ISP and confirm WAN/LAN assignment.
  7. Wait for PPPoE, DNS and Internet reachability; then open Gateway Quality and run Diagnose connection.
  8. Create your first configuration snapshot and encrypted backup.

AI-assisted path — step by step

You can ask an AI agent to help with the deployment, but it can only perform actions in systems it is genuinely connected to. A good request is specific and gives the agent clear safety constraints.

  1. Give the agent access to the correct Minimal Router repository and, if supported, your Proxmox environment/terminal.
  2. Ask it to inspect first — existing bridges, VM IDs, available storage and which NIC/bridge is WAN versus LAN.
  3. Ask it to create a new VM rather than modifying the working router unless you explicitly intend an in-place change.
  4. Have it attach the ISO or deploy the validated Alpine build path and install Minimal Router.
  5. Require it to stop if interface identity is ambiguous instead of guessing WAN/LAN.
  6. After boot, have it verify service state, PPPoE, DNS, Internet, WireGuard and the Startup Timeline.
  7. Only after validation should you make the new VM the active router.
Example request: “Create a new isolated Minimal Router VM in Proxmox using the current signed build. Do not touch the existing production router. Verify WAN/LAN mapping, install, boot, run health checks, and report PPPoE/DNS/WireGuard readiness before I switch traffic.”

First boot checklist

  • Dashboard reachable only from the intended trusted management network.
  • Correct LAN address and DHCP range.
  • PPPoE session established if WAN is enabled.
  • DNS resolves and HTTPS Internet reachability succeeds.
  • System time synchronized.
  • Firmware trust anchor installed if you intend to use signed dashboard updates.
  • WireGuard/DynDNS configured only if needed.
  • Snapshot and encrypted backup created after the first known-good configuration.

Architecture in plain language

How Minimal Router works

The dashboard expresses desired configuration. A narrow privileged apply path validates and applies it. Runtime state is then reconciled against that saved configuration.

Canonical configuration

The saved configuration is the source of truth. Manual Linux changes are not the normal operating model.

Default deny

WAN input is closed unless a path is deliberately permitted. Remote administration is intended to use trusted networks and WireGuard.

Safe changes

Important changes use validation, snapshots and timed rollback rather than blindly replacing live network state.

Local recovery

If networking is broken, recovery is local through Proxmox/physical console and router-recovery.

Monitor

Overview

Your first status page: “is the router healthy, is Internet working, and which devices are here?”

  • WAN/Internet: current uplink state.
  • CPU & memory: current load; short spikes around boot/update/backup are normal.
  • Traffic: receive/transmit counters.
  • Devices: current DHCP leases and known local clients.
  • Health: current apply/configuration and important service state.

Monitor

Gateway Quality

WAN quality, fault isolation and conservative automatic recovery.

Latency and packet loss

Latency is response delay; packet loss is the share of probes that never return. Multiple targets help avoid blaming the ISP when one remote host is down.

Automatic PPPoE recovery

Acts only after sustained PPPoE link-down and uses a cooldown. It does not restart WAN merely because DNS fails or one website is unreachable.

Diagnose connection

Run this before changing settings. It checks the chain in order: PPPoE → public reachability → DNS → HTTPS, so you can distinguish link failure from name-resolution or application-layer failure.

Monitor

LAN & DHCP

WAN credentials, LAN gateway, DHCP leases and local DNS records.

WAN / PPPoEConnects the router to the ISP. Username/password normally come from the ISP.
LAN addressThe router address used by local devices as their gateway and management endpoint.
DHCPAutomatically gives clients an address, gateway, DNS and lease time.
Static leaseReserves a predictable address for a known device.
Static DNS recordCreates a memorable local name such as immich.home.arpa for a fixed IP.

LAN and DHCP changes can disconnect the browser. Review Smart Change Preview and leave Safe Apply armed for management-impacting changes.

Protect

Firewall

Stateful, default-deny WAN policy with explicit forwarding paths.

  • Stateful inspection: replies to connections you initiated are allowed without opening generic inbound access.
  • WAN input: unsolicited Internet traffic is dropped by default.
  • Port forwards: deliberate exceptions. Add only when you understand exactly which service is being exposed.
  • Extra LAN/service rules: isolate or selectively permit local subnets/services.

Prefer WireGuard over exposing management or private services directly to WAN.

Protect

Security

Authentication, trusted management boundaries and recent security events.

Trusted Networks

Only configured management networks are allowed to reach the admin surface. A client outside that boundary is rejected before login.

TOTP / 2FA

Adds a rotating one-time code to the admin login. Correct system time matters for TOTP.

Port Forwards

Security page also surfaces explicit inbound forwarding rules so exposure is visible and intentional.

Security events

Shows recent login, rejection and policy events without storing passwords or request bodies.

Recovery Tools

Recovery actions are deliberately separated from ordinary configuration. Network-breaking recovery belongs on the local console; the web UI should not become a remote root shell.

Protect

DNS Filter & Device Profiles

Domain blocking and scheduled policies for named groups of devices.

  • DNS filtering: returns blocked answers for configured unwanted domains.
  • Device Profiles: group one or more static device IPs under a readable policy name.
  • Service schedules: allow/block selected services during configured local-time windows.
  • Why profiles: one named policy is easier to audit than many unrelated per-device rules.

Schedules depend on router local time, so NTP/chrony must remain healthy.

Connect

QoS / Smart Queue Management

CAKE or FQ-CoDel control bufferbloat — high latency caused by a fully loaded connection.

QoS does not make the ISP line faster. It deliberately shapes slightly below line rate so queues stay under router control instead of building up inside the modem/ISP path.

  1. Disable QoS and run the built-in speed test.
  2. Start with roughly 90% of measured download/upload.
  3. Enable CAKE (recommended) or FQ-CoDel.
  4. Compare latency while the connection is busy.

Connect

WireGuard

Encrypted remote access plus an optional outbound site-to-site/client tunnel.

WireGuard server

Add a remote device, receive a dedicated tunnel IP and download/scan its generated client configuration. Save it immediately; private client material is intentionally not retrievable later.

Outbound client tunnel

Lets this router initiate access to a remote site. The design does not grant the remote site a generic route to initiate new connections into your home LAN.

Peer lifecycle

Each laptop/phone should have its own peer. Disable or delete a peer when the device is lost, retired or no longer trusted. The page also shows recent handshake and transfer state.

Connect

Dynamic DNS

Keeps a hostname pointed at a changing public IP.

This is useful when the ISP changes your address but remote WireGuard clients need a stable endpoint name. Supported provider credentials stay in router configuration and the management UI still does not need to be exposed publicly.

Connect

Wi-Fi Access Point

Runs a local AP when compatible wireless hardware is installed.

Configure radio interface, SSID, band, channel and passphrase. Wi-Fi joins the protected LAN path instead of becoming an unmanaged parallel network. Use a strong passphrase and a sensible local channel.

Operate

Traffic

Interface/device usage for troubleshooting and capacity planning.

Traffic counters show how much data is moving. They are not packet capture and do not store web content. Use them to identify unusually busy clients, compare periods or validate that expected paths carry traffic.

Operate

Squid authenticated forward proxy

A non-caching authenticated proxy with a useful high-isolation workstation pattern.

Normal use

Enable Squid, choose a LAN-only listening port, username and strong password, then configure a supported browser/application to use the router as its HTTP/HTTPS forward proxy.

Restricted workstation pattern

  1. Give the workstation a stable IP.
  2. Add it to the Squid Restricted client list so ordinary direct Internet forwarding is blocked.
  3. Configure the browser with the router LAN IP, Squid port, username and password.
  4. Verify direct outbound Internet fails while browser web traffic through the proxy succeeds.

This means software that simply opens arbitrary direct Internet connections cannot use the normal routed path, while the explicitly configured authenticated browser can still browse through Squid. Squid is non-caching, so it is not intended to store web content or trade freshness for cache speed.

Security limit: this materially reduces network exposure but does not make the endpoint “completely safe.” Browser content can still be malicious, an application explicitly configured for the proxy may use it, and endpoint/LAN security still matters.

Operate

Recovery & Snapshots

Known-good restore points for configuration mistakes and emergency repair.

  • Automatic pre-change snapshots: protect important configuration changes.
  • Manual snapshot: create one before an experiment or maintenance session.
  • Restore: return to a selected verified configuration.
  • Last-known-good: fastest console recovery when you simply want the latest healthy configuration back.
  • Factory reset: last resort; use only when preserving current configuration is no longer useful.

Operate

Logs & Startup Timeline

Audit history plus a boot-by-boot record designed specifically for troubleshooting.

Startup Timeline

The last 5 boots are retained. For the first 10 minutes of each routerd start, Minimal Router records small CPU/RAM samples and first-ready times for management, PPPoE, DNS, Internet and WireGuard.

A healthy sequence might look like +0s routerd → +12s management → +24s PPPoE → +27s DNS → +29s Internet → +34s WireGuard. Compare boots to see where a slowdown first appears.

No passwords, private keys or request bodies belong in this timeline.

Audit events

Records bounded security/configuration metadata such as login results, rejected access, mutations, backup/restore and related actions. Export JSON when collecting evidence for troubleshooting.

Safety

Smart Change Preview & Safe Apply

Understand a change before it can affect the network.

Smart Change Preview summarizes what is about to change, expected risk/interruption and whether timed rollback protection will be armed. Critical network changes use two-phase confirmation: apply, verify you still have management, then Keep changes. If confirmation never arrives, the router restores the previous configuration automatically.

Safety

Encrypted Backup & Restore

Disaster recovery and migration, separate from local snapshots.

Export an encrypted backup and keep it outside the router. Restore uses a preview before apply. Store the backup password separately from the file.

Operational rule: a backup is only proven after a successful test restore on a spare/fresh VM. Local snapshots are not a substitute for off-router backup media.

Safety

Signed Software Updates

A/B firmware staging with a pinned trust anchor and rollback.

Update now

Checks the official release path, selects the matching architecture, verifies the installed firmware signing trust anchor, signed manifest, hashes, appliance layout and compatibility, stages the inactive slot and activates it. Failed activation returns to the previous slot.

Upload signed build

For a local build, upload the signed payload and its matching manifest. Unsigned or mismatched builds are rejected.

Trust anchor

/etc/minimalrouter/firmware-signing.pub must already exist from a trusted bootstrap/full install. The dashboard must never silently trust a public key delivered inside an untrusted update.

Emergency access

Proxmox / Local Recovery Console

Use this when the dashboard is unreachable because the network itself is broken.

How to open it

  1. In Proxmox, select the Minimal Router VM.
  2. Open Console.
  3. Log in as root.
  4. Run router-recovery with no arguments.

Interactive menu

The menu provides interface/status inspection, WAN assignment, LAN/IP repair, restore last-known-good, snapshot selection/restore, authentication recovery, service restart, reboot and a temporary shell. Destructive operations still require explicit confirmation.

No background cost: the recovery menu is a command-line program, not a daemon. It uses no CPU/RAM when it is not open.

Useful CLI equivalents

router-recovery interfaces, set-wan, set-lan, snapshots, restore-last-good, restore-snapshot, reset-auth and factory-reset remain available for emergency/scripted use.

Troubleshooting

Recommended order when something is wrong

Use the least destructive action first.

  1. Overview: identify whether the problem is WAN, resources, one client or a broader appliance issue.
  2. Gateway Quality → Diagnose connection: isolate PPPoE, reachability, DNS or HTTPS.
  3. Logs → Startup Timeline: compare this boot to a known-good boot.
  4. Audit log: check whether a recent configuration/security action explains the change.
  5. Restart only the affected service when the evidence points to one service.
  6. Restore last-known-good or a snapshot when the issue began after configuration changes.
  7. Factory reset only as a final recovery path.

Glossary

Common terms used by the dashboard.

PPPoEISP login/session carried over Ethernet; commonly used on fiber connections.
WANThe Internet-facing side of the router.
LANYour private local network behind the router.
DHCPAutomatically assigns network settings to local clients.
DNSTurns names such as example.com into IP addresses.
NATAllows private LAN addresses to share the WAN connection.
Stateful firewallTracks connections so replies are allowed without opening arbitrary inbound access.
WireGuardModern encrypted VPN/tunnel protocol.
QoS / SQMTraffic shaping designed to control latency and fairness under load.
A/B updateNew firmware is staged to the inactive slot so the previous slot remains available for rollback.
SnapshotLocal verified configuration restore point.
Trust anchorThe already-installed public signing key that determines which firmware signatures are trusted.
Minimal Router reduces attack surface through explicit trust boundaries, privilege separation, safe defaults and verified recovery paths. No router can make an unsafe endpoint, stolen credential, compromised hypervisor or malicious browser content inherently safe.
