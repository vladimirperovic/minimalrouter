# Minimal Router OS v0.4.2

**Status:** Unpublished candidate for controlled-pilot Beta. Publication requires
the exact-commit release gates; this file is not evidence that they have passed.

This candidate includes the unpublished v0.4.1 preparation, subsequent security
audit fixes and repairs to the QEMU Lab harness. The earlier detailed
[review](https://github.com/vladimirperovic/minimalrouter/blob/v0.4.2/docs/SECURITY-REVIEW-0.4.1.md) distinguishes confirmed defects from
intentional trade-offs and additional hardening. See the
[validation record](https://github.com/vladimirperovic/minimalrouter/blob/v0.4.2/docs/CURRENT_VALIDATION.md) for the remaining release gates.

## Changes

- Firmware staging stays root-private until the copied signed inventory is
  verified. Source reads reject symlinks throughout the path, special files,
  oversized payloads and size changes. Manifest reads use the same protected
  path handling with a 1 MiB cap.
- PPPoE passwords beginning with `@/` are rejected before generating secrets
  files, preventing pppd from treating an administrator-supplied password as a
  file to read. Quotes alone do not disable pppd's file indirection.
- Login attempts rejected by the per-source limiter no longer consume the
  global login budget. Distributed flooding can still exhaust that budget.
- DHCP/DDNS state ownership and permissions are changed through checked file
  descriptors, eliminating the path replacement race. Symlinks and unexpected
  file types remain fail-closed; this does not guarantee availability after
  compromise of a service account.
- Lab fuzzing restores a server-side snapshot with its secrets intact, checks
  every restoration and confirms only the transaction returned by its own
  operation. Deterministic seed replay and WAN precondition reporting make
  failures attributable. The speed-test action rejects unsolicited request
  bodies before changing QoS or accessing the network.

- Changed WireGuard clients retire the old peer session and require a new
  post-activation handshake, even with
  keepalive disabled. Both processes use the same freshness/future-time rules.
- Trusted networks reject overly broad public ranges and masked unspecified
  networks while preserving existing ULA and normal CIDR host-bit semantics.
- applyd returns connection capacity after handler panic and rejects oversized
  IPC frames rather than silently truncating them.
- HTTP sockets have a 30-second write inactivity timeout. Ambiguous request
  framing, overflowing Content-Length and invalid header names are refused;
  VT content sniffing is corrected.
- DNS risk classification releases the feed publication lock before SQL queries.
  DNS filtering reuses bounded catalog connections, reaps finished workers and
  records panics as unconfirmed outcomes requiring review.
- Persistent bearer session identifiers are hashed; legacy plaintext sessions
  are revoked. Backup and MCP-owned secret buffers use erasure guards.
- TLS files are created private, update-channel preferences are synced, archive
  extraction validates the root before writing and uses bounded permissions,
  and revision arithmetic refuses overflow.

- The management HTTP server applies absolute read deadlines, a total TLS
  handshake deadline, bounded chunked trailers, a header-count limit and a
  per-source connection limit. The static `index.html` redirect is relative.
  WireGuard server peer endpoint ports are validated.
- SSH on the LAN and WireGuard interfaces is accepted only from the IPv4 members
  of `trusted_networks`; an explicit drop of new tcp/22 on the same interface
  precedes the custom firewall rules, so a custom rule cannot widen SSH. There is
  no packet-level rate limit on new connections
  (scripted administration opens one per command); new appliances start `sshd`
  with `MaxAuthTries 4`, `LoginGraceTime 30` and `PerSourceMaxStartups 4`.
- Firstboot refuses a recovery (root) password shorter than 12 characters, reads
  it without echo and sets it with `chpasswd -c sha512`; it stops with an error
  if echo cannot be switched off.
- Service log lines are sanitised and capped, log lines for unauthenticated
  requests are rate-limited, and the installers enable `crond` with a 15-minute
  job that rotates the service logs.

- Four production-parser fuzz targets run with AddressSanitizer in CI,
  with daily longer campaigns and weekly corpus pruning. The isolated QEMU
  Lab also runs weekly. Targeted mutation tests verify WG/IPC regression quality.
  See [FUZZING.md](https://github.com/vladimirperovic/minimalrouter/blob/v0.4.2/docs/FUZZING.md).

## Upgrading

Appliances at or below v0.4.1, including development installations of unpublished
candidates, need the full signed distribution installer once: shared validation,
storage and firmware changes affect bootstrap tools outside the A/B slot.
An A/B web update cannot replace those tools. Preserve signature, architecture,
version-floor and runtime-layout checks.
A complete replacement OS comes from a Golden ISO on a blank disk/VM followed by
firstboot and encrypted configuration restore. The live ISO still only verifies
and raw-copies its image; existing disks remain protected against overwrite.

SSH from the LAN or WireGuard is now refused for sources outside
`trusted_networks`; an appliance whose `trusted_networks` holds no IPv4 network
has no SSH access until one is added. The `crond` and log-rotation job arrive
with the full installer or a new Golden image, not with an A/B web update; the
`sshd` limits and the recovery-password minimum apply to appliances installed or
first booted after this change.

Before upgrading, narrow any trusted ranges the new validation rejects. Expect
a fresh login after migration. When changing an idle WireGuard client without
keepalive, generate tunnel traffic and confirm only after a new handshake;
otherwise let the normal confirmation timeout roll back the change.

## Validation

See [CURRENT_VALIDATION.md](https://github.com/vladimirperovic/minimalrouter/blob/v0.4.2/docs/CURRENT_VALIDATION.md) for collected evidence.
Windows tests and Linux cross-compilation do not establish installed appliance
behavior. CI, CodeQL, Secret scan, Deep validation, Performance, Service
supervision, Appliance ISO and the complete QEMU Lab must pass on the exact
candidate. The signed release then repeats full installation with the signed
payload before publication. No real ISP, physical NIC, power-cut or unattended
production validation is claimed.
